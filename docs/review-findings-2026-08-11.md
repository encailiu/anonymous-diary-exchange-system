## 4. 詳細

### REV-01: 再送時にDeliveryLogとMatchesの対応を検証しない

**根拠**

- 実装仕様は、既存マッチの日記・参加者対応、自己マッチ、重複などを配信前に検証するよう定めている: [実装仕様](4-impl-spec-v1.0.md#5-配信状態と再送仕様)
- 初回配信は既存マッチを `validateMatchesForDiaries_()` で検証する: [`main.gs`](../src/main.gs#L41)
- 再送処理はDeliveryLog内の重複と、日記・有効参加者の存在だけを確認して送信する: [`main.gs`](../src/main.gs#L155)

**影響**

DeliveryLogが手動編集、部分障害、誤った復旧操作などで破損した場合、現在のMatchesで指定された相手ではない有効参加者へ日記を送信できる。匿名性より先に防ぐべき誤配信リスクである。

**推奨する解決策**

1. 再送開始時に、対象日のMatchesを有効日記に対して検証する。
2. Matchesから許可される `diary_id + recipient_participant_id` の集合を生成する。
3. 再送対象のDeliveryLogがその集合に1件だけ対応することを確認する。
4. 対応しない行、余分な行、欠落行、未知のstatusがあれば、1通も送信せず全管理者へ通知する。
5. DeliveryLogの `recipient_email` は監査用とし、現在のParticipantsとの不一致も警告または停止条件にするかを仕様で決める。

**完了条件**

- マッチと無関係な `error` 行を用意したテストで送信件数が0件になる。
- 正常な `error` 行だけが1回再送される。
- `processing` と `delivered` は再送されない。
- 不整合時に全 `ADMIN_EMAILS` への通知が試行される。

### REV-02: 長時間の単一Script Lockが受付処理を失敗させ得る

**根拠**

- 共通ロックは30秒で取得できなければ例外にする: [`utils.gs`](../src/utils.gs#L36)
- 日次交換はマッチ作成、写真変換、Gmail送信、状態更新の全体でロックを保持する: [`main.gs`](../src/main.gs#L10)
- Form受付とコメント受付も同じScript Lockを使用する: [`diary.gs`](../src/diary.gs#L1)、[`comments.gs`](../src/comments.gs#L30)
- 22:00:00以降の投稿は翌日分として有効であり、日次配信時間と重なる: [要求仕様](2-require-spec-v1.0.md#4-投稿締切と配信時間)

**影響**

日次交換やアーカイブが30秒を超えると、その間の翌日分FormトリガーやコメントPOSTが失敗する可能性がある。Form回答がGoogle Forms側に残ってもDiariesへ反映されず、現在は再同期機能がない。コメント側では参加者に受付失敗が表示される。

**推奨する解決策**

1. ロックが必要な状態読込・予約・更新と、Gmail・Slides・UrlFetchなどの外部I/Oを分離する。
2. 外部I/O前に一意な `processing` 状態を予約し、別実行が同じ処理を予約できないようにする。
3. ロック解放後の送信結果を、再取得した行のIDとstatusを確認してから反映する。
4. Form回答とDiariesを照合し、未取り込み回答を管理者が安全に再同期できる復旧機能を設計する。
5. コメント、日記受付、日次配信、アーカイブを同時実行した競合テストをGoogle検証環境で実施する。

ロック範囲の変更は二重送信防止に直接影響するため、実装前に状態遷移図と異常終了点を確定する。

**完了条件**

- 30秒を超える日次処理中でも、翌日分投稿が欠落しない。
- 同時コメントPOSTでも同じ `submission_token` の通知は1通だけになる。
- 送信成功後の状態更新失敗は `processing` のまま残り、自動再送されない。
- Formトリガー失敗後の再同期を2回実行しても重複日記が作られない。

### REV-03: Gmail差出人情報と完全匿名性の説明が一致しない

**根拠**

- 参加者へ名前、メールアドレス、Googleアカウント情報を公開しないことを要求している: [要求仕様](2-require-spec-v1.0.md#6-完全匿名性)
- `sendSystemMail()` は差出人オプションを指定せず、Gmail実行ユーザーから送信する: [`mail.gs`](../src/mail.gs#L1)
- セットアップは個人の無料Googleアカウントでの構成を許容している: [セットアップ](../SETUP.md#1-用意するもの)

**影響**

日記の書き手の情報は本文へ出力されないが、メールのFromヘッダーに管理者個人の名前とメールアドレスが表示され得る。現在の「Googleアカウント情報を公開しない」という説明を文字どおり満たさない。

**推奨する解決策**

1. 「隠す対象が参加者相互の情報だけか、管理者・システム所有者も含むか」を要求仕様で確定する。
2. 管理者の個人アカウントではなく、個人名を含まない専用システムGoogleアカウントを所有者・送信者として必須化する。
3. `sendSystemMail()` で表示名を固定のシステム名にする。
4. Google Workspace限定のno-reply機能には依存せず、無料個人アカウントでも成立する運用を正本にする。
5. VERIFICATIONへFrom、Reply-To、表示名、アバターなど受信メールのメタデータ確認を追加する。

**完了条件**

- 参加者の受信画面・メールヘッダーに管理者個人の名前や個人用アドレスが表示されない。
- 日記本文、添付、コメントURLにも書き手の識別情報がない。
- 使用可能なアカウント種別と匿名性の限界がSETUPとREADMEで一致する。

### REV-04: 最大50人・写真付き運用の実行制限対策がない

**根拠**

- 将来50人程度までを想定している: [要求仕様](2-require-spec-v1.0.md#2-想定参加人数)
- 写真付き日記ごとに一時Presentationを作成し、最大3枚を個別にPNG出力する: [`mail.gs`](../src/mail.gs#L43)
- 日次処理は全配信を単一実行で処理する: [`main.gs`](../src/main.gs#L63)

**影響**

参加者数、写真数、コメント数が増えると、Apps Scriptの1実行時間、メール送信先数、Presentation作成、UrlFetchなどの制限に達する可能性がある。途中停止してもDeliveryLogにより二重送信は抑制されるが、当日中に全件配信できない可能性がある。

**推奨する解決策**

1. 実行開始時に残りメール送信枠を確認し、不足時は送信前に停止して管理者へ通知する。
2. 1回の処理件数または残り実行時間を基準に分割し、未処理の `pending_delivery` を次のトリガーで再開できるようにする。
3. 写真0枚・1枚・3枚、参加者20人・30人・50人で実測時間を記録する。
4. クォータ上限値をソースへ固定せず、Google公式情報が変更され得ることをSETUPに明記する。
5. 50人運用で必要な日記配信、想定コメント通知、管理者通知を合算した容量計画を作る。

**完了条件**

- 50人・写真3枚の負荷試験結果と、対応可能な上限が文書化される。
- 制限到達時に未送信行が安全な状態で残り、実行結果が成功扱いにならない。
- 再開処理を複数回実行しても二重送信されない。

### REV-05: 直近ペア履歴に未配信・失敗マッチも含まれる

**根拠**

- 要求仕様は「過去7日間に交換した組み合わせ」を避けるとしている: [要求仕様](2-require-spec-v1.0.md#5-ランダム交換マッチング規則)
- 実装はMatches.statusを見ず、期間内の全 `match_type=pair` を履歴に含める: [`history.gs`](../src/history.gs#L5)

**推奨する解決策**

次のどちらを正本とするか、実装前に決定する。

- マッチ作成済みなら、配信結果にかかわらず「同じ相手を割り当てた履歴」として避ける。
- 両方向が `delivered` の場合だけ「交換済み」として避ける。片方向だけ配信された場合の扱いも定める。

決定後、要求仕様の文言と `getRecentPairKeys_()` の条件、テスト名・期待値を一致させる。

### REV-06: スキップ履歴が対象日より後のデータに影響される

**根拠**

- `getSkipHistory_()` は全Matchesを集計し、シート上の最後のスキップ行を前回スキップ者にする: [`history.gs`](../src/history.gs#L16)
- 管理メニューから過去の指定日を実行できる: [`admin.gs`](../src/admin.gs#L38)

**推奨する解決策**

1. `getSkipHistory_(diaryDate)` のように対象日を渡す。
2. `diary_date < 対象日` の有効なスキップ行だけを集計する。
3. 前回スキップ者はシート行順ではなく、最新の `diary_date` と必要なら `created_at` で決める。
4. 過去日を後から実行するテストと、行順を入れ替えたテストを追加する。

### REV-07: 未解決状態を含む旧データを削除できる

**根拠**

- アーカイブ対象は有効な `diary_date < beforeDate` だけで決まり、statusを確認しない: [`admin.gs`](../src/admin.gs#L58)
- 削除後は通常の配信再送、processing解決、コメント通知再送ができない。

**推奨する解決策**

次の状態が対象範囲に1件でもあれば、既定ではアーカイブを停止する。

- `DeliveryLog.status` が `error` または `processing`
- `Comments.status` が `error` または `processing`
- `Matches.status` が `pending_delivery`、`processing`、`error` または未知の値

運用上、未解決のまま終了させる必要がある場合は、別の明示的な終結状態と管理者確認手順を仕様化する。また、Diaries削除後は既発行のコメントリンクが無効になることを確認画面とSETUPへ明記する。

**完了条件**

- 未解決状態があるとCSV作成・行削除の前に停止する。
- 解決済みデータだけの場合は従来どおり、4 CSVとマニフェストの検証後に対象行だけ削除する。
- 基準日当日以後と不正・欠落日付の行は保持される。

### REV-08: Participantsの内容整合性を検証しない

**根拠**

- 読み込み処理は重複ID・重複メールを後の行で上書きする: [`participants.gs`](../src/participants.gs#L1)
- 管理メニューはメール重複だけを確認し、手動編集された既存行全体は検証しない: [`participants.gs`](../src/participants.gs#L22)

**推奨する解決策**

マッチングと配信前に参加者マスター全体を検証し、以下のいずれかに違反した場合は送信前に停止する。

- `participant_id` が空でなく一意である。
- 正規化したメールアドレスが空でなく一意である。
- メールアドレスが最低限の形式検証を通る。
- `active` が `true` または `false` のどちらかである。
- 同じ参加者を示す競合行が存在しない。

検証エラーには参加者向け情報を含めず、全管理者へ処理コンテキストを通知する。

**推奨する解決策**

- REV-03の匿名性範囲を確定した後、要求仕様、README、SETUP、VERIFICATIONを同時に更新する。
- 実環境で未検証の事項は「設計上防止している」「検証完了後に本番開始する」など、実証状況が分かる表現にする。

## 6. 対応時に維持する不変条件

- 参加者へ氏名、メールアドレス、内部ID、Googleアカウント情報、管理URLを表示・送信しない。
- `DeliveryLog.status` を配信状態の正本とし、送信結果不明の `processing` を自動再送しない。
- すべての送信は `sendSystemMail()` を経由する。
- 日次処理、再送、アーカイブの共有状態変更にはロックを使い、`finally` で解放する。
- 例外と送信失敗は全 `ADMIN_EMAILS` へ通知し、参加者情報を含めず処理コンテキストを残す。
- アーカイブの検証成功前に元データを削除せず、基準日当日以後や不正・欠落日付の行に触れない。
- Google標準機能だけで完結させ、有料外部サービスや外部APIを追加しない。
